# 2026-08-12 — 딜레이 전수 조사

사장님 신고 3줄:
1. "메인PC 딜레이가 엄청 길고 아이패드만 정상 속도"
2. "딜레이 차이 때문에 치우면 지워졌다가 다시 되살아나는 경우가 생긴다"
3. "안드로이드 탭도 딜레이가 심하다"

②가 결정적이었다 — 딜레이와 부활이 **한 뿌리**라는 뜻이고, ③은 "웹 전용 문제"가
아니라 **기기 CPU 속도** 축이라는 뜻이다 (아이패드 빠름 / 안드로이드 탭·저사양 PC 느림).

## 오늘 처방한 것

### ① TableScreen 깜빡임 타이머가 영구 가동 — 분당 100회 전체 리렌더
`screens/TableScreen.js:79`

```js
setInterval(() => setBlinkOn((b) => !b), 600);   // mount 즉시, 무조건, 영구
```

`blinkOn` 은 테이블 강조 **3초**(`blinkActive`) 에만 쓰이는데 타이머는 앱 켜둔 내내
산다. 탭은 전부 mount 상태(`display:none`)라 테이블 탭을 안 보고 있어도 돈다.
TableScreen 은 그리드·타일·영수증 계산이 거의 memo 안 돼 있어 매 틱마다 전부 재계산.

→ `blinkActive` 동안만 가동. 평소 0회. **웹·안드로이드 양쪽에 듣는다.**

### ② 주소록을 매 변경마다 통째로 localStorage 에 직렬화
`utils/useOrderPersistence.js:144`

`entries`/휴지통은 Firestore 가 단일 진실이고 부팅 복원도 **안 하는데**(6/9 처방),
저장만은 매 변경마다 전체를 `JSON.stringify` 했다. 웹의 AsyncStorage 는
localStorage = **동기 블로킹**, 네이티브는 비동기 — PC 만 멎던 비대칭의 정체.

→ 복원에 실제로 쓰는 메타 4개만 저장. 주소 데이터 손실 0. **웹 전용 처방.**

### ③ 디바운스 기아 → 삭제가 서버로 안 감 → 부활
`utils/useOrderFirestoreSync.js` (orders / history / addresses 3경로)

push 는 `orders` 가 바뀔 때마다 타이머를 취소하고 300ms 뒤로 다시 잡는다. 그런데
`orders` 는 내 조작뿐 아니라 **다른 기기 snapshot 이 올 때마다도** 바뀐다 — listener
가 매번 새 객체를 만들어 hydrate 하므로 내용이 같아도 참조가 달라지기 때문.

```
테이블 치움 → 로컬 삭제 → 300ms 뒤 커밋 예약
  ↓ 아이패드 write → snapshot → 예약 취소, 다시 300ms
  ↓ 주방 write   → snapshot → 예약 취소, 다시 300ms
  ↓ (느린 기기라 콜백이 밀려 더 촘촘해짐)
→ 커밋이 영영 안 뜸. 삭제가 서버로 못 감.
```

화면에선 사라진다(`mergeKeyedPull` 이 미push 로컬 삭제를 지켜줌). 서버엔 살아 있다.
→ 새로고침·재시작·재접속의 첫 snapshot(전체 교체)에서 **부활**.
느린 기기에서만 재현되는 이유도 기아 조건이 CPU 속도에 걸려서다.

→ 디바운스 상한(orders 2초 / 이력·주소록 3초). 늦어질 수는 있어도 사라질 수는 없게.

## 조사에서 나온 지연원 9건 — 전부 처방 완료

> 사장님 지시 "전부 적용하고 배포까지" 로 B1~B9 를 같은 날 전부 처방했다.
> 아래는 **무엇이 문제였고 어떻게 고쳤는지** 의 기록이다.
> (한 번에 하나씩이 원칙이었으나 사장님 판단으로 일괄 적용 — 대신 웹 번들 빌드
> 검증 + jest 763 으로 회귀를 막았다.)

### 🔴 B1. 주소 자동 좌표변환 루프 — O(N²) + 쓰기 폭주
`utils/useAddressBook.js:100-158` · **상시 활성 (패널 안 열어도 돈다)**

effect deps 가 `addressBook.entries` 인데, 결과 하나가 도착할 때마다
`setAddressBook` → entries 새 객체 → **effect 재실행 → 전 항목 재스캔**.
동시 호출 상한도 없다.

주소록 1,000건 / 좌표 없는 항목 50건이면:

| 비용 | 횟수 |
|---|---|
| 전 항목 재스캔 | 50 × 1,000 = **5만 회** |
| 카카오 동시 호출 | **50건 동시 발사** |
| Firestore addresses write | **50건** |
| snapshot 수신 + 전체 앱 리렌더 | **50회** |

**"저장 횟수가 오버 되면서 딜레이" 와 구조가 가장 닮은 살아있는 코드.**
6/11 사고(`ignoredSimilarPairs` union 무한루프)는 진짜 무한루프였고 이건 유한하지만,
한 번에 터지는 양은 비슷하다.

**처방** — `utils/lazyEnrichQueue.js` 신설, 동시 실행 3건 상한 + 결과 400ms 일괄 반영.
카카오 동시 호출 50 → 3, 전체 앱 리렌더 50회 → 1~2회. 성공한 키는 반영 전까지
in-flight 로 유지해 재요청도 막는다. jest 7케이스(상한/코얼레싱/늦은 결과 flush/
throw 복구/reset).

> 성능 옵션 **주소 자동 좌표변환 OFF** 로도 여전히 통째 회피 가능 (그대로 둠).

### 🔴 B2. 주소록 패널 도로거리 fetch 루프 — B1과 완전 동형
`components/AddressBookPanel.js:222-284` · 관리자 → 주소록 **열었을 때만**

같은 O(N²) + 동시 호출 무제한 + 결과마다 Firestore write.
사장님이 주소록 화면 열어두면 그 동안 계속 돈다.

**처방** — B1 과 같은 `lazyEnrichQueue` 로 교체. 코드 형태까지 통일.

### 🟠 B3. 매출이력 1,000건 통째 실시간 구독
`utils/useOrderFirestoreSync.js:232-251`

결제 1건 = **전 기기가 문서 1,000개를 `d.data()` 로 재생성** → 새 배열 → context 값
교체 → 화면 5개 전부 리렌더. 7/3 커밋에 "다음은 docChanges 증분으로" 라고 남겨둔 항목.
안드로이드 탭에도 그대로 부담이다.

**처방** — id → data 캐시 + `docChanges()` 증분 갱신. 바뀐 문서만 `d.data()` 하고
나머지는 캐시 객체 재사용. 배열 순서는 `snap.docs` 기준 그대로 재구성해 정렬/표시
동작 무변경. `docChanges` 를 못 쓰는 SDK/첫 snapshot 은 전량 재구성으로 폴백
(웹은 메서드, RNFirebase 는 버전에 따라 프로퍼티 — `readDocChanges` 가 흡수).

### 🟠 B4. 탭 5개 상시 mount + context 값이 통짜
`App.js:694` (`paneHidden: { display: 'none' }`) · `utils/OrderContext.js:1020`

context `useMemo` deps 가 `orders / splits / revenue / groups / addressBook` — **하나만
바뀌어도 값 전체가 교체**되고 5개 화면이 전부 리렌더된다. 게다가 listener 는 내용이
같아도 새 객체를 만들어 hydrate 하므로 **내용 무변화 snapshot 도 전체 리렌더**를 부른다.

B1·B3 의 피해를 5배로 증폭시키는 구조. 여기가 근본이지만 수술도 제일 크다.

**처방(부분)** — `revenue` 만 `RevenueContext` 로 분리. 값 안에서 revenue 를 *읽는*
곳이 `revertHistoryEntry` 한 군데뿐이라 ref 로 돌리면 끝나는, 위험이 닫힌 수술이었다.
읽는 화면 4개(수익현황/되돌리기/배달회수/주문-추천)만 `useRevenueData()` 로 구독 →
**결제·매출이력 변경이 더는 테이블·주방 화면을 리렌더하지 않는다.** 액션(markPaid 등)은
`setRevenue` 함수형 갱신이라 그대로 OrderContext 에 남아 호출부 수정 0.

orders/splits/groups/addressBook 은 서로 얽혀 있어 이번엔 분리하지 않았다 — 남은 몫.

### 🟠 B5. KitchenScreen 목록 계산 비메모
`screens/KitchenScreen.js:234-249`

```js
const allOrders = Object.entries(orders).filter(...).filter(...).sort(...)
```
`useMemo` 없이 매 렌더 재계산. 항상 mount 상태라 B4 의 리렌더를 그대로 받는다.
테이블 수가 적어 절대 비용은 작지만 TableScreen 과 같은 계열.

**처방** — `allOrders` / `activeOrders` 를 `useMemo([orders])` 로. `resolveTable` 이
모듈 함수만 쓰므로 deps 는 orders 하나로 닫힌다.

### 🟡 B6. 카카오 API 타임아웃 없음
`utils/geocode.js:77` (`callKakao`) · `:199` (`getDrivingDistance`)

`AbortController` 가 없다. 응답이 안 오면 `inFlightRef` 가 **영구 잠금** → 그 항목은
앱 재시작 전까지 재시도 불가. 브라우저 연결 슬롯도 계속 물고 있어 뒤에 선 Firestore
요청까지 밀린다. `ipWatcher`(8초)·`latestVersion` 은 타임아웃 있음 — 카카오만 빠졌다.

**처방** — `fetchWithTimeout` (8초, `AbortController` 없는 환경은 자동 우회) 로 3곳
전부 교체.

### 🟡 B7. menu_rows self-heal 되쓰기 — 잠재 무한 루프
`utils/MenuContext.js:277-293`

listener 가 `recovered` 면 Firestore 에 되쓴다 → echo snapshot → listener 재실행.
**현재 기본값 6종이 전부 비어있지 않아 1회로 수렴** (지금은 안전).

단 `defaultCategoryRows` 에 전부-null 카테고리가 하나라도 생기면
`reconcileRowsWithDefaults` 가 매번 `recovered: true` 를 내서 → 되쓰기 → echo →
또 recovered → **무한 쓰기 루프**. 6/11 한도 사고와 정확히 같은 형태.

**처방** — 직전에 쓴 값의 서명(`JSON.stringify(encoded)`)을 ref 에 기억하고 같으면
쓰지 않는다. 조건이 성립해도 write 는 1회에서 멈춘다.

### 🟡 B8. addressBookMeta 의 state/ref 계산 불일치
`utils/useOrderFirestoreSync.js:296-313`

state 는 fallback 을 적용(`meta.todayDate || prev.todayDate`,
`Array.isArray(...) ? ... : []`)하는데 ref 는 **서버 원본을 그대로** 저장한다.
서버에 필드가 없으면 둘이 어긋나 write 가 한 번 더 난다 — 지금은 그 write 후
수렴하지만, 수렴하지 않는 필드가 하나만 추가돼도 무한 루프가 된다.

**처방** — `resolved` 를 한 번 계산해 **state 와 ref 에 같은 객체**를 넣는다.
어긋날 수 있는 경로 자체를 없앴다.

### 🟡 B9. 메뉴 listener 가 snapshot 마다 새 배열
`utils/MenuContext.js:237-267`

merge + shortName 마이그레이션이 매 snapshot 새 배열을 만들어 `setItems` →
MenuContext 값 교체 → 전체 리렌더. 메뉴는 자주 안 바뀌어 실피해는 작다.

**처방** — `sameMenuItems` 얕은 비교로 내용이 같으면 기존 배열 유지 → 리렌더 0.
메뉴가 25개 안팎이라 비교가 리렌더보다 훨씬 싸다.

## 남은 것 / 다음 확인

1. **배포 후 🩺 성능 진단 재측정** — 관리자 → 시스템. 200ms+ 블로킹이 남는지,
   어떤 이름표(`⚙ 저장:...` / `⚠ 매출이력 문서 N개`)가 뜨는지가 다음 판단 근거.
2. **B4 잔여** — orders/splits/groups/addressBook context 분할. revenue 만 떼어냈다.
   서로 얽혀 있어 실행 검증 없이는 위험. 진단에서 리렌더 병목이 계속 잡히면 그때.
3. **이미 서버에 남은 좀비** — 이번 처방은 *원인* 을 없앤 것이다. 디바운스 기아로
   삭제가 못 올라간 채 서버에 살아있는 테이블이 있다면 그건 별개로 남는다.
   특정 테이블이 계속 되살아나면 그 건만 따로 봐야 한다.
