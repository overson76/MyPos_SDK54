## 무엇이 바뀌었는가

| 질문 | 답 |
|---|---|
| 왜 기기끼리 달랐나 | 서버가 차단돼 각 기기가 로컬 저장본으로만 돌았다 |
| 왜 재시작·롤백이 안 통했나 | 앱 문제가 아니라 서버가 막힌 것이라서 |
| 왜 쓰기 2만이나 했나 | `orders[tid] !== synced[tid]` 참조 비교 → 에코 오판 → 자가증식 루프 |
| 왜 읽기까지 터졌나 | 쓰기 1건 = 다른 기기 수만큼 읽기 에코. 2만 × 3대 ≈ 6만 |
| 루프를 켠 건 | 그날 낮 배포한 자동 재연결(재연결 후 낡은 기준선으로 dirty 병합) — 롤백 |
| 6/10 사고와 관계 | **완전히 같은 계통.** 그때 필드 하나만 빼고 판정 방식은 남겨둬 재발 |
| 재발 방지 | 내용 비교(deepEqual) + 총량 상한(writeGuard) + 사용량 가시화 |
| Spark 다운그레이드와 무관한가 | **무관하지 않다.** Blaze 때는 초과분이 과금됐고 Spark 는 차단된다 |

## 핵심 기술 결정

- **참조 비교 → 내용 비교.** 동기화 판정을 참조로 하면 언젠가 반드시 루프가 난다.
  단, 최상위 가드는 싼 참조 비교로 남겼다 — 저사양 카운터 PC 부담(7/3 멈춤 이력).
- **원인을 하나씩 잡지 않고 총량 상한을 건다.** 원인은 매번 다른 모습으로 온다
  (6/10 union 배열, 9/11 참조 비교). 분당 300 이 루프 차단의 주력.
- **일일 상한 = 서버 한도 ÷ 기기수.** 2만 ÷ 5대 = 4천.
- **자동 복구는 하지 않는다.** 유령 매장·권한 상실 모두 표식만 남기고 판단은 사장님.
  오탐 한 번이 영업 중 전 기기를 내쫓는다.
